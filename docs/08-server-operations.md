# Server Operations Reference

**The relay VPS: what runs on it, how to operate it, and what to do when something breaks.**

Related: [`sitectl` usage](07-sitectl-usage-and-api.md) · [architecture](SYSTEM-ARCHITECTURE.md) · script [`scripts/sitectl`](../scripts/sitectl)

---

## What is running

Three components, all on one VPS.

| Component | Job | Port |
|---|---|---|
| **WireGuard** (`wg0`) | Encrypted tunnel to each site's Android box | 51820/UDP |
| **MediaMTX** | Pulls RTSP through the tunnel, serves WebRTC to viewers | 8889/TCP, 8189/UDP |
| **sitectl** | Provisions sites across both of the above | — |

```
Viewer ──WebRTC──▶ MediaMTX ──RTSP──▶ WireGuard ──▶ Android box ──▶ DVR
                                                      (relay app)
```

MediaMTX only opens the RTSP connection when a viewer is actually watching, and closes it 10 seconds after they leave. No viewer means no traffic and no cost.

---

## File locations

```
/etc/relay/
├── relay.env               server-wide settings — edit once
├── sites.db                THE SOURCE OF TRUTH for all sites
├── keys/                   one keypair per site + the server's
├── client-configs/         configs to paste into boxes
└── backups/                mediamtx.yml before each change

/etc/wireguard/wg0.conf     generated — do not hand-edit
/root/mediamtx.yml          generated by sitectl — do not hand-edit
/usr/local/bin/sitectl      the provisioning tool
```

**Only `sites.db`, `keys/` and `relay.env` are irreplaceable.** Everything else regenerates from them with `sitectl sync`.

# Daily operations

## Check everything is healthy

```bash
sitectl list                      # sites and last handshake
systemctl status mediamtx         # is the relay server up
wg show                           # raw tunnel state
```

`sitectl list` output:

```
SITE         TUNNEL IP    CHANNELS  LAST HANDSHAKE
site001      10.8.0.3     4         42s ago
site002      10.8.0.4     4         never
```

**Last handshake is the health signal:**

| Value | Meaning |
|---|---|
| Under 2 minutes | Connected and healthy |
| 2–5 minutes | Possibly dropping — watch it |
| Over 5 minutes | Site is offline |
| `never` | Config never applied to the box |

With keepalive at 25 seconds, a healthy site handshakes every ~2 minutes.

## Watch the logs

```bash
journalctl -u mediamtx -f          # live
journalctl -u mediamtx -n 100      # last 100 lines
journalctl -u mediamtx --since "1 hour ago"
```

## Add a site

```bash
sitectl add site003 --dvr-pass 'TheActualPassword' --channels 4
```

| Flag | Default |
|---|---|
| `--dvr-user` | `admin` |
| `--dvr-pass` | required |
| `--channels` | 4 |
| `--json` | off |

Quote passwords containing special characters. **Type the real password** — the value is used verbatim.

It prints the WireGuard config and a QR code. Paste or scan that into the box's WireGuard app.

## Remove a site

```bash
sitectl remove site003
```

Removes the peer, keys, config and MediaMTX paths. Its tunnel IP is never reused.

## Re-print a config

```bash
cat /etc/relay/client-configs/site001.conf
qrencode -t ansiutf8 < /etc/relay/client-configs/site001.conf
```

## Change something about a site

Edit the registry and sync:

```bash
nano /etc/relay/sites.db
sitectl sync
```

Format:

```
name|tunnel_ip|dvr_user|dvr_pass|channels|public_key|created
```

`sitectl sync` rebuilds WireGuard peers and MediaMTX paths from that file. Safe to run any time.

# MediaMTX

## Service control

```bash
systemctl status mediamtx
systemctl restart mediamtx
systemctl stop mediamtx
systemctl start mediamtx
systemctl enable mediamtx         # start at boot (already done)
```

## Config changes do not need a restart

MediaMTX watches its config file and hot-reloads on change. Look for this in the log:

```
INF reloading configuration (file changed)
```

`sitectl` writes the config **in place** rather than replacing it, specifically so the file watcher notices. If you ever change that behaviour to `mv`, hot reload silently stops working and MediaMTX keeps running the old config.

If a reload does not appear in the log after a change, restart manually.

## Config structure

```yaml
pathDefaults:
  rtspTransport: tcp              # REQUIRED — see below
  sourceOnDemand: yes
  sourceOnDemandCloseAfter: 10s

paths:
  site001_ch1:
    source: rtsp://user:pass@10.8.0.3:8554/Streaming/Channels/102
  site001_ch2:
    source: rtsp://user:pass@10.8.0.3:8554/Streaming/Channels/202
```

**`rtspTransport: tcp` is not optional.** The relay on the box is a plain TCP byte copier and cannot carry RTP over separate UDP ports. The default is `automatic`, which tries UDP first and times out after 10 seconds. `pathDefaults` applies it to every path so it cannot be forgotten on a new site.

## Path naming and channel numbers

Path names are `<site>_ch<n>`. The stream ID in the URL is **channel × 100 + stream type**, where 1 = main and 2 = sub.

| Camera | Main | Sub |
|---|---|---|
| 1 | 101 | 102 |
| 2 | 201 | 202 |
| 4 | 401 | 402 |

`sitectl` always generates sub-streams — lower bandwidth, and they must be **H.264 with H.264+ enabled** on the DVR (see [SYSTEM-ARCHITECTURE §7.4](SYSTEM-ARCHITECTURE.md#74-encoding-per-channel--main-and-sub)).

## Viewing URLs

```
http://<vps-ip>:8889/<site>_ch<n>
```

Use **Firefox** while on plain HTTP; Chrome blocks WebRTC without HTTPS.

### HTTPS setup (for `relay.truvend.online`)

**Full guide:** [`backend/plexity-ai-chat/bash/HTTPS-RELAY.md`](../../../backend/plexity-ai-chat/bash/HTTPS-RELAY.md)

```yaml
# /root/mediamtx.yml (+ sitectl mtx_regenerate HEADER)
webrtc: yes
webrtcAddress: 127.0.0.1:8889
webrtcLocalUDPAddress: :8189
webrtcAdditionalHosts: [relay.truvend.online]
```

```bash
ufw allow 8189/udp
systemctl restart mediamtx
```

View: `https://relay.truvend.online/<site>_ch<n>`

## Check the API

```bash
curl -s http://127.0.0.1:9997/v3/paths/list | python3 -m json.tool
```

Lists every configured path and whether it is currently active.

# WireGuard

## Inspect

```bash
wg show                              # all peers
wg show wg0 latest-handshakes        # just handshake times
ip addr show wg0                     # interface address
```

## Manual peer operations

Normally `sitectl` handles this. If you need to do it directly:

```bash
# add a peer live, without dropping other sites
wg set wg0 peer <PUBLIC_KEY> allowed-ips 10.8.0.9/32
wg-quick save wg0

# remove
wg set wg0 peer <PUBLIC_KEY> remove
wg-quick save wg0
```

**Never restart WireGuard to add a peer.** `wg-quick down && up` drops every connected site. `wg set` applies immediately and touches nothing else.

Restarting is only needed when changing something in `[Interface]` — the server's own address, port or private key:

```bash
wg-quick down wg0 && wg-quick up wg0
```

## Config reference

Server (`/etc/wireguard/wg0.conf`):

```ini
[Interface]
Address = 10.8.0.1/16
ListenPort = 51820
PrivateKey = <server private>

[Peer]                        # one block per site
PublicKey = <site public>
AllowedIPs = 10.8.0.3/32      # that site's address only
```

Client (on the box):

```ini
[Interface]
PrivateKey = <site private>
Address = 10.8.0.3/32

[Peer]
PublicKey = <server public>
Endpoint = relay.truvend.online:51820
AllowedIPs = 10.8.0.0/16
PersistentKeepalive = 25
```

**`[Interface]` means "me", `[Peer]` means "the other end".** Each side holds its own private key and the other side's public key. A private key never crosses the network.

**Two client settings that must be right:**

- `AllowedIPs = 10.8.0.0/16` — routes only tunnel traffic through the tunnel. Setting `0.0.0.0/0` captures LAN traffic too, so the relay can no longer reach the DVR **while the tunnel looks perfectly healthy**.
- `PersistentKeepalive = 25` — without it, routers drop the idle UDP mapping and the tunnel dies when nobody is watching. It revives the instant you test it, so it appears to work every time you check.

# Diagnosing a broken stream

Work outward from the DVR. Each step isolates one layer.

## 1. Is the site connected?

```bash
sitectl list
```

`never` or a handshake over 5 minutes old means the tunnel is down. Nothing else can work — fix that first.

## 2. Can the server reach the relay?

```bash
nc -zv -w 5 10.8.0.3 8554
```

- **Succeeds** → relay is listening
- **Times out** → packets are not arriving, or the relay is not bound to the tunnel interface

Ping is not a useful test here — Android often does not reply to ICMP on the WireGuard interface even when healthy.

## 3. Does the relay reach the DVR?

```bash
printf 'OPTIONS rtsp://x RTSP/1.0\r\nCSeq: 1\r\n\r\n' | nc -w 3 10.8.0.3 8554 | head -5
```

- **`RTSP/1.0 200 OK`** → DVR is answering
- **Nothing** → the relay connects and is dropped immediately, so the DVR address in the app is wrong or the DVR is off
- **`HTTP/1.1 ...`** → the relay is pointing at port 80, not 554

## 4. Full path test

```bash
ffprobe -rtsp_transport tcp rtsp://admin:PASSWORD@10.8.0.3:8554/Streaming/Channels/102
```

Success:

```
Stream #0:0: Video: h264 (High), yuv420p, 704x576, 15 fps
```

**Must say `h264`.** If it says `hevc`, the DVR's sub-stream is still H.265 and WebRTC will not play it — fix it in the DVR under *Record → Encoding → Sub-Stream* (set codec to **H.264** and enable **H.264+** so bitrate/stream size stays manageable).

`-rtsp_transport tcp` is required, for the same reason MediaMTX needs `rtspTransport: tcp`.

## 5. If ffprobe works but the browser does not

The problem is MediaMTX config. Check:

```bash
grep -A3 "site001_ch1" /root/mediamtx.yml
```

- Path missing → the site is not in `sites.db`, run `sitectl sync`
- Wrong password → fix in `sites.db`, run `sitectl sync`
- Wrong tunnel IP → same

## Error message index

| Message | Meaning |
|---|---|
| `path 'X' is not configured` | No such path — the site is not in the registry, or you used the wrong URL |
| `[RTSP source] timed out` | Nothing answered at the tunnel address. Tunnel down, or `rtspTransport` not set to tcp |
| `[RTSP source] EOF` | Connected, then dropped. Usually wrong DVR password |
| `Invalid data found when processing input` | Connection accepted but closed immediately. Relay cannot reach the DVR |
| `Network is unreachable` | Wrong address — you used a LAN address (192.168.x.x) from the VPS. Use the tunnel address |
| `No route to host` | No peer at that tunnel address. Check `wg show` |
| `bind: address already in use` | A second MediaMTX is running. `pkill mediamtx` then start once |

# Backup

The registry and keys cannot be regenerated. Everything else can.

```bash
tar czf relay-backup-$(date +%F).tar.gz /etc/relay
gpg -c relay-backup-*.tar.gz          # contains private keys — encrypt it
```

Store off the server. Losing `/etc/relay` means visiting every site in person to re-provision.

**Restoring:**

```bash
tar xzf relay-backup-*.tar.gz -C /
sitectl sync
```

That rebuilds `wg0.conf` and `mediamtx.yml` from the registry.

# Known gaps

Things not yet done, in the order they will matter.

| Gap | Consequence |
|---|---|
| **HTTPS not configured** | Chrome refuses WebRTC over plain HTTP — see “HTTPS setup” above (`webrtcAddress` / `webrtcAdditionalHosts` / `webrtcLocalUDPAddress`) |
| **No authentication** | Anyone who guesses a path URL can watch that camera |
| **No heartbeat** | You learn a site is down when the customer calls |
| **DVR passwords in plaintext** in `sites.db` | `chmod 600`, but a database with encryption is the eventual answer |
| **Config pasted by hand** into each box | Fine for a handful of sites; an enrolment API replaces it later |
| **Embedded WireGuard unreliable** | Standalone WireGuard app with Always-on VPN is the current workaround |
